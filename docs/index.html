Security architecture / review deck

Secure
Apache APISIX

Kubernetes + Bare Metal · Traditional + Standalone · HashiCorp Vault

Design review — not production-approved

Target: APISIX 4.x. Exact release, Helm chart and configuration schema require compatibility validation.

01 / Objective

What are we protecting?

Configuration

Versioned, reviewed, validated, recoverable.

Secrets

Vault-backed; no credentials in Git or presentation assets.

Management plane

Admin API and etcd isolated from public traffic.

Principles: least privilege · defense in depth · auditable changes.

03 / Modes

Traditional vs Standalone

Traditional

  • Dynamic configuration through Admin API
  • etcd for configuration storage
  • Restrict writer identities and management network
  • Backup/restore etcd

Standalone (file-driven)

  • Declarative apisix.yaml
  • No traditional etcd dependency
  • Git review + atomic file rollout
  • Validate config before promotion
04 / Kubernetes

Kubernetes deployment controls

Helm / workload

  • Pin compatible chart + image digests
  • Dedicated namespace and ServiceAccount
  • Non-public Admin Service
  • Pod Security Context / read-only mounts where compatible

Cluster boundary

  • Default-deny NetworkPolicy with explicit allowances
  • Encrypt Kubernetes Secrets at rest
  • Vault Kubernetes Auth / operator
  • Disable bundled etcd when external or standalone
05 / Bare Metal

Bare Metal deployment controls

Ansible

  • Idempotent configuration templates
  • Least-privilege Linux service identity
  • File ownership and permissions
  • Validate before controlled reload

Host security

  • Firewall / private admin network
  • Vault Agent with machine auth
  • Tested systemd hardening
  • OS logs + patch management
06 / Vault

Vault is the secret source of truth

K8s

Kubernetes Auth
→ Vault policy
→ operator/agent

Bare Metal

Machine identity / AppRole
→ Vault Agent
→ restricted file

Separate policies by service and environment. Rotate credentials; do not expose Vault tokens, secret values or rendered secret files in GitHub Pages.

08 / Baseline

Minimum security acceptance

  • Admin API not internet-accessible
  • Default credentials replaced
  • etcd TLS + authentication
  • Vault least-privilege policies
  • No plaintext secrets committed
  • Review + validation before deploy
  • Audit logging enabled
  • Restore and rollback tested
09 / Risks

Open validation items

Compatibility

Confirm exact APISIX 4.x release exists and is supported; verify config schema, Vault support, and Helm chart compatibility.

Operational behavior

Test reload semantics, Vault outages, secret rotation, etcd failure and cert expiry in staging.

Exposure

Review service type, ingress, network policies, firewall rules and CI logs.

Recovery

Document RPO/RTO and perform restore drills for both deployment modes.

10 / Decisions

Decisions for this review

  • Which exact APISIX release and Helm chart version?
  • Which mode for each environment and workload?
  • How will Vault authentication and rotation work?
  • Who may change dynamic routes or promote releases?
  • What are the rollback and disaster-recovery targets?
